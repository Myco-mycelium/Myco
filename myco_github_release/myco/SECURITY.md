# Security Policy

## Myco Security Model

Myco is an open-source, locally-run AI agent. Security is a first-class concern — especially because Myco can autonomously generate and execute code through its self-improvement engine.

---

## Threat model

| Threat | Mitigation |
|---|---|
| Prompt injection | Pattern-based scanner on every message; flagged inputs blocked before reaching the LLM |
| LLM-generated malicious code | 3-layer sandbox: AST whitelist → restricted builtins → subprocess with OS resource limits |
| Sandbox escape | No imports allowed; no file I/O; no network; subprocess killed after 3 seconds |
| Unauthenticated API access | Bearer token required for every endpoint except `/health` |
| Privilege escalation | Role-based access (parent > user > readonly); each role has an explicit permission set |
| Runaway self-improvement | Master kill-switch; parent approval required for all code and prompt changes |
| Audit tampering | SHA-256 hash chain; every entry includes hash of previous; `GET /audit/verify` detects tampering |
| Data exfiltration in sandbox output | Output screened for URLs, credentials, and sensitive path patterns |
| Supply-chain (malicious imports) | `import` and `from ... import` are banned AST nodes — code never imports anything |
| Resource exhaustion | CPU, memory, file descriptor, and process limits enforced per sandbox run |
| Token brute force | PBKDF2-HMAC-SHA256 with 100k iterations for token hashing |
| Rate limit abuse | Per-token sliding-window rate limits, configurable per role |

## Security layers in order

### Layer 1 — Input screening
Every `/chat` and `/ingest` message is scanned for 12 prompt-injection patterns before the LLM ever sees it. Detected attacks are logged to the audit trail and blocked with a `400` response.

### Layer 2 — Authentication
All API endpoints require a Bearer token. Tokens are PBKDF2-hashed (never stored in plaintext), role-checked, and rate-limited. The parent token is printed once at startup (or set via `MYCO_PARENT_TOKEN` env var).

### Layer 3 — Sandbox (for all generated code)
Every piece of code generated by Myco's self-improvement engine goes through three sequential gates:

```
Code string
    │
    ▼
[Gate 1] Static analysis (AST walk)
  - Banned nodes: import, from-import, global, nonlocal, async defs, await, yield
  - Banned strings: eval, exec, open, __import__, subprocess, socket, os.path, etc.
  - Any violation → REJECTED (code never runs)
    │
    ▼
[Gate 2] Subprocess execution
  - Runs in a separate OS process (not just a thread)
  - Restricted builtins: ~40 safe functions, no file/network/process builtins
  - Resource limits: 3s wall clock, 2s CPU, 256 MB RAM, 4 file descriptors, no fork
  - Killed automatically if it exceeds limits
    │
    ▼
[Gate 3] Output screening
  - Checks output for URLs, credentials, SSH keys, sensitive paths
  - Suspicious output → verdict SUSPICIOUS (not integrated)
    │
    ▼
[Gate 4] Parent approval (for new_tool and prompt_patch)
  - Code that passed the sandbox is queued, not auto-integrated
  - A parent token holder must approve via POST /self-improve/approve/{plan_id}
  - Plans can be rejected with a reason
    │
    ▼
[Gate 5] Mind snapshot + re-sandbox at integration
  - A snapshot of the full mind state is taken before every integration
  - The code is sandbox-tested one final time at integration
  - Any exception triggers automatic rollback to the pre-integration snapshot
```

### Layer 4 — Audit log
Every security-relevant event is written to an append-only SQLite table with a SHA-256 hash chain. The chain links each entry to the previous one, making retroactive tampering detectable. Call `GET /audit/verify` to check chain integrity at any time.

## Responsible disclosure

If you find a security vulnerability in Myco, please **do not open a public GitHub issue**.

Instead:
1. Email `security@myco.dev` (or open a private GitHub Security Advisory)
2. Include a description of the vulnerability and reproduction steps
3. Allow up to 90 days for a fix before public disclosure

We take all reports seriously and will credit researchers in the changelog.

## Known limitations

- **Sandbox on non-Linux systems**: The `resource` module's hard limits (`RLIMIT_CPU`, `RLIMIT_AS`, `RLIMIT_NPROC`) are Linux-only. On macOS and Windows the subprocess still runs in an isolated process with restricted builtins and a wall-clock timeout, but OS-level memory and CPU enforcement is not available. For production deployments on non-Linux hosts, run Myco inside a Docker container.

- **Token storage**: Tokens are stored in memory (lost on restart) in the default configuration. For multi-instance or persistent deployments, replace `TokenStore` with a Redis or Postgres backend.

- **AST-based injection detection is heuristic**: The 12 prompt-injection patterns cover known attack vectors but cannot guarantee detection of all novel approaches. Treat the scanner as defence-in-depth, not a complete guarantee.

- **LLM-generated knowledge (knowledge_fill)**: Knowledge filled autonomously by the self-improvement engine is screened for injection patterns but is not otherwise fact-checked. Enable parent approval for knowledge fills in high-stakes deployments by adding `"knowledge_fill"` to `REQUIRES_APPROVAL` in `growth.py`.

## Hardening checklist for production

- [ ] Set `MYCO_PARENT_TOKEN` environment variable (don't rely on the auto-generated one)
- [ ] Set `MYCO_CORS_ORIGINS` to your exact frontend origin (not `*`)
- [ ] Run behind a reverse proxy (nginx/Caddy) with TLS — never expose port 8000 directly
- [ ] Run inside Docker with `--read-only`, `--no-new-privileges`, `--cap-drop ALL`
- [ ] Set `self_improve_enabled: false` in config until you've reviewed the approval queue flow
- [ ] Create user-role tokens for end users; keep parent token offline
- [ ] Schedule `GET /audit/verify` as a cron job and alert on failure
- [ ] Rotate tokens regularly via `DELETE /tokens/{id}` + `POST /tokens/create`
- [ ] Review `GET /self-improve/pending` before approving any plans

## Running the security test suite

```bash
pip install pytest
pytest safety/tests/ -v

# Expected output: all tests PASSED
# Any FAILED test indicates a regression in the security layer
```

The test suite covers:
- 12 sandbox static-analysis cases
- 8 sandbox execution cases (including timeout and recursion bomb)
- 6 token lifecycle tests (create, verify, expire, revoke)
- 5 role permission tests
- 2 rate limit tests
- 10 injection detection tests
- 6 audit chain integrity tests (including tamper detection)

## Open source and security

Myco is open source because transparency is itself a security property. The full sandbox code, injection patterns, and auth logic are readable by anyone — which means they can be independently audited, improved, and verified.

Security through obscurity is not our model. If an attacker can bypass our sandbox knowing exactly how it works, that is a real vulnerability we need to fix — not hide.
